# Project Folders Refactor

**Date:** 2025-01-22
**Status:** Approved
**Type:** Architecture Change + Security Fix

## Problem Statement

### Critical Security Issue
The current implementation copies ALL private SSH keys from `~/.ssh/` into the golden template, including personal keys. This means:
- Private keys are baked into a template file anyone can mount and extract
- Every VM gets the same keys (no isolation)
- Sharing snapshots means sharing private keys
- No per-repo deploy key support

### Architecture Issues
1. `workspace.json` has dual purposes: 10% functional config, 90% unused LLM context
2. No support for multiple project configurations
3. Config files scattered (user's home directory)
4. No clear separation between template data and project data

## Solution Overview

### Security Fix
- Golden template contains ONLY host public key for SSH access
- NO private keys in template
- Deploy keys injected per-VM from project configurations
- Each VM gets only the keys it needs

### New Architecture
- Project-based configuration in `projects/` folder within repo
- Clean separation: git-config.json (functional) + .md files (context)
- Per-repo SSH deploy keys
- Multi-project support with VM reusability

## Design

### 1. Project Folder Structure

```
agent-foundry/
  projects/
    example-project/              # Example (tracked in git)
      git-config.json             # Repository configuration
      overview.md                 # Project context
      architecture.md             # Architecture docs
      .ralph/                     # Optional (Ralph-specific)
        PROMPT.md
        fix_plan.md
        AGENT.md
        specs/
      deploy-key-example          # Deploy key (private)
      deploy-key-example.pub      # Deploy key (public)

    acme-company/                 # User's config (git ignored)
      git-config.json
      company-context.md
      coding-standards.md
      backend-deploy-key
      backend-deploy-key.pub
      frontend-deploy-key
      frontend-deploy-key.pub
```

**Git Ignore Strategy:**
```gitignore
# Ignore all project configs except the example
projects/*
!projects/example-project/
```

**Benefits:**
- Users customize in repo, never commit sensitive keys
- Multiple project configs supported
- One project can spawn multiple VMs
- Clear structure for users to follow

### 2. git-config.json Format

**File:** `projects/<project-name>/git-config.json`

```json
{
  "repositories": [
    {
      "name": "backend",
      "url": "git@github.com:acme/backend.git",
      "branch": "main",
      "ssh_key": "backend-deploy-key"
    },
    {
      "name": "frontend",
      "url": "git@gitlab.com:acme/frontend.git",
      "branch": "develop",
      "ssh_key": "frontend-deploy-key"
    },
    {
      "name": "shared-lib",
      "url": "git@github.com:acme/shared.git",
      "branch": "main",
      "ssh_key": "backend-deploy-key"
    }
  ]
}
```

**Fields:**
- `name`: Directory name in VM (`/work/<vm>/repos/<name>/`)
- `url`: Standard git SSH URL (domain extracted automatically)
- `branch`: Branch to checkout (default: "main")
- `ssh_key`: Filename of deploy key in project folder (without .pub)

**Multiple repos can share the same deploy key.**

### 3. SSH Key Setup in VM

**Process during VM creation:**

1. **Copy deploy keys** from project folder to VM:
   - `projects/my-project/backend-deploy-key` → `/root/.ssh/backend-deploy-key`
   - Set permissions: `chmod 600`

2. **Generate `/root/.ssh/config`** automatically:

```ssh-config
# Auto-generated by Agent Foundry

Host github.com-backend
    HostName github.com
    User git
    IdentityFile ~/.ssh/backend-deploy-key
    StrictHostKeyChecking no

Host gitlab.com-frontend
    HostName gitlab.com
    User git
    IdentityFile ~/.ssh/frontend-deploy-key
    StrictHostKeyChecking no

Host github.com-shared-lib
    HostName github.com
    User git
    IdentityFile ~/.ssh/backend-deploy-key
    StrictHostKeyChecking no
```

**Pattern:** `Host <domain>-<repo-name>`

3. **Clone repos with modified URLs:**
   - Original: `git@github.com:acme/backend.git`
   - Modified: `git@github.com-backend:acme/backend.git`
   - SSH uses correct key via Host alias

**Security Benefits:**
- Each VM gets only needed keys
- Keys never in template
- Per-repo isolation
- Standard SSH config approach

### 4. VM Workspace Structure

**After:** `foundry vm create dev-vm --project acme-company`

```
/work/dev-vm/
├── AGENT.md              # Generic entrypoint (from template)
├── .ralph/               # Copied if exists (Ralph users only)
│   ├── PROMPT.md
│   ├── fix_plan.md
│   ├── AGENT.md
│   └── specs/
├── context/              # User's .md files
│   ├── company-context.md
│   └── coding-standards.md
├── memory/               # Empty for agent to populate
│   ├── decisions.md
│   ├── progress.md
│   ├── learnings.md
│   └── blockers.md
├── repos/                # Cloned repositories
│   ├── backend/
│   └── frontend/
└── logs/                 # Agent execution logs
```

**File Copying Logic:**
- `AGENT.md` ← Always from `templates/AGENT.md.template`
- `.ralph/` ← Copied recursively IF exists in project folder
- `context/*.md` ← All `.md` files from project folder (except in .ralph/)
- `memory/` ← Empty template files for agent
- `repos/` ← Git clones using generated SSH config

**AGENT.md Template Content:**

```markdown
# Agent Instructions

## Project Context
- See files in `context/` for project overview, architecture, standards

## Working Memory
- `memory/decisions.md` - Track architectural decisions
- `memory/progress.md` - Track implementation progress
- `memory/learnings.md` - Document patterns learned

## Repositories
- Source code is in `repos/`
- See git-config.json for repository details

## Agent-Specific Config
- Ralph users: See `.ralph/` folder
- Other agents: Create your own workflow files
```

**Design Notes:**
- Generic for any agent (Ralph, Claude Code, Gemini)
- User can customize AGENT.md in project folder
- Not required to customize (works out of box)

### 5. Golden Template Changes

**Current Behavior (INSECURE):**
```bash
# scripts/build-golden.sh line 355-363
copy_ssh_keys "$mount_dir/root/.ssh" "${FOUND_HOST_HOME}/.ssh"
# ❌ Copies ENTIRE ~/.ssh including private keys
```

**New Behavior (SECURE):**
```bash
# Modified function
setup_host_ssh_access "$mount_dir/root/.ssh" "$ssh_public_key"
# ✓ Only copies public key to authorized_keys
# ✓ NO private keys
# ✓ NO deploy keys (those come per-VM)
```

**Golden Template Contains:**
- Host public key in `/root/.ssh/authorized_keys` (for `foundry vm ssh`)
- System packages and AI tools
- **Nothing else SSH-related**

**Golden Template Does NOT Contain:**
- ❌ Private SSH keys
- ❌ Git deploy keys
- ❌ User's personal keys

**Impact:**
- Template safe to share/snapshot
- No security concerns with distribution
- Keys isolated per-VM

### 7. Implementation Changes

**Files to Modify:**

**A. `bin/foundry`**
- Parse `--project <name>` in vm create
- Validate project folder exists
- Pass to workspace_init

**B. `lib/workspace.sh`**

**New signature:**
```bash
workspace_init "$vm_name" "$project_dir"
# $project_dir = "projects/acme-company"
```

**New helper functions:**
```bash
_setup_ssh_keys() {
    # 1. Copy deploy keys from project_dir to VM /root/.ssh/
    # 2. Generate /root/.ssh/config with Host aliases
    # 3. Set permissions (600 on keys)
}

_copy_project_files() {
    # 1. Copy AGENT.md template to workspace root
    # 2. Copy .ralph/ if exists
    # 3. Copy all .md files to context/
}

_init_memory_files() {
    # Keep existing - creates empty memory files
}

_clone_repositories() {
    # Modified to use generated SSH Host aliases
    # git clone git@github.com-backend:acme/repo.git
}
```

**Functions to Remove:**
```bash
_copy_context_files()      # No longer needed
_validate_config_file()    # workspace.json validation
```

**C. `scripts/build-golden.sh`**

**Replace:**
```bash
copy_ssh_keys "$mount_dir/root/.ssh" "$ssh_source"
```

**With:**
```bash
setup_host_ssh_access "$mount_dir/root/.ssh" "$ssh_public_key"

setup_host_ssh_access() {
    local target_ssh_dir="$1"
    local public_key_path="$2"

    mkdir -p "$target_ssh_dir"
    chmod 700 "$target_ssh_dir"

    # Copy ONLY public key to authorized_keys
    cat "$public_key_path" > "$target_ssh_dir/authorized_keys"
    chmod 600 "$target_ssh_dir/authorized_keys"

    # NO private keys copied
}
```

## Migration Impact

**Breaking Changes:**
- `--config workspace.json` flag removed
- workspace.json no longer supported
- Old VMs continue working, but new ones require --project

**User Migration Path:**
1. Create project folder: `projects/my-project/`
2. Create `git-config.json` with repos
3. Add deploy keys to project folder
4. Add context .md files
5. Use: `foundry vm create vm1 --project my-project`

**No backward compatibility** - clean break approach.

**Risk:** Users accidentally commit private keys
**Mitigation:** .gitignore strategy (allow only example-project)

**Risk:** SSH config generation bugs
**Mitigation:** Thorough testing with multiple git hosts (GitHub, GitLab)

**Risk:** Breaking existing users
**Mitigation:** Clear documentation, no backward compatibility (clean break)
